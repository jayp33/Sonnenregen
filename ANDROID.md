# Sonnenregen Android app

## Goal

Sonnenregen should also be a native Android app showing a permanent notification
with both forecasts for one or more locations (default: Berlin):

- how long until the sun shines, or until the current sunshine ends;
- how long until it rains, or until the current rain ends.

The app fetches and parses the WetterOnline pages itself. It does **not** depend
on the Python HTTP service in this repository. That service remains useful as a
reference implementation and for debugging, but the mobile app is standalone.

## Platform decisions

- **Kotlin + Jetpack Compose**, minSdk 26 (or enable core library desugaring if
  supporting older versions, for `java.time.OffsetDateTime`).
- **WorkManager** for periodic work. A 15-minute interval is the minimum
  supported by WorkManager, and is accepted for this app. This avoids
  foreground-service restrictions entirely.
- No foreground service. `ACTION_USER_PRESENT` / `ACTION_SCREEN_ON` are not
  exempt implicit broadcasts on API 26+, so a manifest receiver cannot reliably
  trigger an immediate refresh. Instead we rely on Doze: WorkManager jobs are
  deferred while the device is in Doze and are run when it becomes active again,
  so a pending 15-minute job normally executes shortly after unlock. This gives
  refresh-on-unlock without an FGS. If truly exact unlock timing is required,
  that is a separate design change involving a foreground service and its
  Android 12+/15+ constraints.
- The notification is still "permanent" in the sense that it is posted as an
  ongoing notification (`setOngoing(true)`); the system keeps it visible even
  when the app process is killed.

## Localization

All user-facing text lives in Android resources. `values/strings.xml` is the
English fallback; `values-de/strings.xml` contains the German translation.
Android selects the translation from the device locale, so a German-locale
device gets German text and other locales keep the English fallback.

The forecast wording is generated by `ForecastFormatter` from `ForecastPhrases`,
which reads the templates from resources. The domain model only carries
structured data (`Change`, `Condition`, `minutes`), never display strings.
German durations use `Std.`/`Min.` instead of `h`/`min`:

- `Sonne in 2 Std. 10 Min., kein Regen`
- `Regen in 30 Min., Sonne in 5 Std.`

## Multiple cities

The user can add and remove WetterOnline city slugs in the app. `normalizeCity()`
trims/lowercases input and `isValidCitySlug()` validates each path segment with
`^[a-z0-9]+(?:-[a-z0-9]+)*$` before any URL is built. Small places can have a
two-part WetterOnline path: enter it exactly as the path after `/wetter/`, for
example `michelbach-an-der-bilz/gschlachtenbretzingen` (not just
`gschlachtenbretzingen`, with the `ch` after `schla`). Slugs remain
lowercase in storage. The add form lives in an `AlertDialog` opened by the +
FAB; its `OutlinedTextField` takes focus and opens the keyboard as soon as the
dialog appears, so typing can start without an extra tap. Remove, the ↑/↓ reorder
controls and a **Show in notification** switch
live inside the expanded per-city details, so none of them clutters the default
view. Those controls also appear when a city has no forecast yet (or its fetch
failed), so a broken city can always be removed. A small muted eye-off icon
next to the city name marks cities excluded from the notification; it keeps the
`hidden` / `ausgeblendet` text as its accessibility label. `ForecastParser` also reads
the human-readable place name
from the page heading (`<h1>`), falling back to `<title>` and then
`displayCity()`. Page boilerplate such as ` - 4 Tage Vorhersage` is stripped,
while hyphens inside real names (`Garmisch-Partenkirchen`) are kept. That name
is persisted with the forecast and used by both the
app and the notification, so `frankfurt-oder` becomes `Frankfurt (Oder)` and
`michelbach-an-der-bilz/gschlachtenbretzingen` becomes
`Gschlachtenbretzingen` instead of a hyphenated slug. DataStore holds:

- `cities`: a JSON array in the user's current order (add order initially, then
  adjustable with the ↑/↓ controls in each city's details). Non-blank entries are
  kept even if they no longer look like valid slugs, so they stay visible and
  removable;
- `forecasts_by_city`: a JSON map from slug to the last good formatted forecast,
  including its real `displayName`. Keys are normalized and each entry is decoded
  independently, so one bad forecast cannot hide the others.
- `hidden_from_notification`: a JSON array of slugs excluded from notification
  statuses but still shown in the app; missing means none are hidden.

The original single-city keys are read once and migrated on first access, so an
existing installation keeps its Berlin forecast after the upgrade.

One worker run fetches every configured city concurrently. Each city is handled
independently:

- a successful city replaces its stored forecast;
- a failed city keeps its last good forecast and is marked stale for that
  notification only;
- the run succeeds if any city succeeded, retries if every failure was a network
  error, and fails if every failure was a parse/validation error.

Adding a city enqueues an immediate refresh; removing one reposts the notification
without a network request. With no cities configured the notification shows an
empty-state line. The Compose screen collects `citiesFlow` and `forecastsFlow`
from the same DataStore, so worker writes and add/remove edits appear immediately
without reopening the activity.

Freshness is shown in two places: a global `Updated x min ago` under the app
title uses the oldest successful fetch across cities (the same rule as the
notification), and each collapsed details block shows the same relative label for
that city alone. Both tick once per minute while the screen is open; `just now`
covers the first minute, then minutes/hours/days are abbreviated and localized.

## 48-hour colour overview

Each city card also shows a colour-only forecast grid: 48 one-hour cells from the
current hour, grouped into four blocks of six per calendar day in the city's own
offset as supplied by WetterOnline (`-05:00` for New York, `+01:00` for Berlin,
and so on). An evening start therefore produces three rows (part of today, all
of tomorrow, part of the day after); exactly midnight produces two. Each row
starts with a short localized weekday (`Mo`/`Di`/…, `Mon`/`Tue`/…) in a fixed-width
column, so all rows line up. A slightly larger gap every six hours is the only
in-row orientation aid — no `00`/`06`/`12`/`18` labels — and no scrolling is needed.
The grid sits directly under the city line. The city line plus grid is one
tappable region; tapping it toggles that city's Sun, Rain, sunrise/sunset,
freshness, reorder and Remove controls, so the colours stay uncluttered by
default and no "Show details" button is needed.

Below the day rows, an optional `90` row shows the 90-minute nowcast as six
15-minute cells with the same colours and a fixed-width prefix matching the
weekday column. These cells are taller than the hourly ones and print their
start time (`21:15`, `21:30`, …) inside, in black on pale shades and white on
the darker rain blues and pinks. It is rendered only when at least one of those
cells is sun, rain or snow.
Day rows use a tight 2 dp vertical gap, while the `90` row is separated by 10 dp
in total (6 dp of extra padding on top of the card's 4 dp) so it reads as a
distinct block; the values live in `WeatherRowSpacing`.
The cells come from the raw `nowcast_trend` items (or the hourly page's nearcast
as fallback), not from the stretched timeline slots. `CityForecast.nowcastCells`
defaults to an empty list, so old installs simply have no extra row until the
next refresh.

Each `HourCell` stores that offset as `zoneId`, so even a DST change inside the
48-hour window keeps the right local hours. Cells stored by older versions
default to `Europe/Berlin` until the next refresh.

The grid reads purely as weather at a glance. Night symbols (`m*`) normally get
no sun colour, so no pale yellow appears before sunrise or after sunset. One
exception: when sunrise or sunset falls inside a one-hour slot, WetterOnline
labels that whole hour with a night symbol. The colour grid uses the matching
day symbol for such boundary hours, so it agrees with the sun text — e.g. an
`mb` hour straddling a 07:41 sunrise becomes pale yellow (`wb`/`PARTLY_SUN`).

- bright/pale yellow — sunny (`so`) / partly sunny (`wb`), day symbols only;
- very light gray — all clouds and night symbols outside those boundary hours;
- light/medium/dark blue — light rain / rain / heavy rain;
- light/medium/dark pink — light snow / snow / heavy snow (`sn1`/`sn2`/`sn3`).

The pink shades come from WetterOnline's own radar precipitation legend
(`#ffc2ff`, `#f969bf`, `#ea39a1` for light/medium/heavy), so the grid matches
the website rather than inventing a snow colour.

For example, `so` is bright yellow, `wb` is pale yellow, and the four night
symbols are very light gray unless their hour straddles sunrise/sunset. Sunrise
and sunset stay in the text line instead of being encoded as glyphs. No weather
icons are drawn; the weekday prefix comes from localized `weekday_*`
strings. Each cell carries a localized
`contentDescription` for screen readers. The
overview is stored as `CityForecast.hours` (defaulting to an empty list), so
existing installs simply show no grid until their next refresh. Legacy night
enum values from the first grid version still decode; `CLEAR_NIGHT` now renders
gray like clouds. The notification is unchanged.

## Data source and parsing

The app fetches both pages with OkHttp (or Ktor), concurrently:

```
https://www.wetteronline.de/wettertrend/{city}
https://www.wetteronline.de/90-minuten-wetter/{city}
```

Use a normal browser-like `User-Agent` and `Accept-Language: de-DE`.

Each page is an Angular SSR app. Parse the embedded state with a regex:

```kotlin
Regex("""(?is)<script[^>]*\bid=["']ng-state["'][^>]*>(.*?)</script>""")
```

Then:

1. JSON-decode the captured script content with `kotlinx.serialization`
   (`ignoreUnknownKeys = true`).
2. Find the state entries whose keys contain `/blending/shortcast/v1?` and
   `/astro/days/v1?`. The latter carries exact per-day `sun.rise` / `sun.set`
   timestamps (and is optional — polar days have neither).
3. Read `current`, `nowcast_trend.items` (15-minute slots) and `hours`
   (1-hour slots). Each item has an ISO-8601 `date` and a `symbol` code.
4. Stitch the 15-minute grid to the hourly grid, as in the Python reference:
   use the fine grid for the near future and stretch its last slot to the next
   full hour.
5. Classify each slot:
   - **sunshine**: symbol starts with `so` or `wb`, and for the current
     observation `solarElevation > 0`;
   - **rain**: symbol contains `r`, `s` or `g` after the first two characters,
     but not snow (`n`);
   - **snow**: symbol contains `n` after the first two characters, with its
     digit (`sn1`/`sn2`/`sn3`) selecting light/medium/heavy. Both grids use
     WetterOnline's radar pink shades (`#ffc2ff`, `#f969bf`, `#ea39a1`), and a
     snow summary line appears in the city details when snow is expected.
6. Split the timeline at sunrise/sunset and mark the parts that are in daylight.
   WetterOnline labels the whole hour containing sunrise with a night symbol
   (e.g. `mo` = *klar*); on the daylight side of the cut we use the matching day
   symbol (`so` = *sonnig*). This makes a clear night start sunshine at the
   exact sunrise instead of at the next hourly grid boundary. Cloudy night
   symbols (`mw` → `bw`) still delay sunshine until a genuinely sunny slot, and
   a sunny slot can never extend past sunset.
7. Walk forward from the provider's `current.date` to the first slot where each
   condition changes. Produce `currently`, `event` (`starts` / `ends`), `at`,
   `minutes`, and a human-readable summary. The next sunrise and sunset are also
   carried on the forecast and shown in the app UI (not in the notification).

City slugs are normalized and validated by the shared helpers in `domain/City.kt`
before building URLs. Nested slugs such as
`michelbach-an-der-bilz/gschlachtenbretzingen` are passed through as one path, so
both `/wettertrend/<slug>` and `/90-minuten-wetter/<slug>` keep the parent.

## Refresh behaviour

`WeatherWorker` is enqueued as a `PeriodicWorkRequest` with a 15-minute interval
and constraints `NetworkType.CONNECTED`, not requiring charging or idle.

On each run:

1. Fetch and parse both pages for **each** configured city, concurrently. Do
   **not** skip the run based on `PowerManager.isInteractive()`; see the note
   below.
2. On success, persist that city's result plus timestamp in DataStore and include
   it in the notification.
3. On failure, keep that city's last good result, show `Weather unavailable` for
   it, and let WorkManager retry with backoff. Other cities are unaffected.

### Why the worker must not skip while the screen is off

An early draft had the worker check `isInteractive()` and do nothing when the
screen was off. That is a staleness bug: WorkManager's periodic run happens at a
wall-clock cadence, so if every screen-on period is short and misses those
moments, the worker can skip indefinitely and the notification never updates.

Doze already provides the desired "idle while screen off" behaviour for the
common case: a phone that is unplugged, stationary and screen-off enters Doze,
WorkManager/JobScheduler defers periodic jobs, and the pending job runs when the
device wakes on unlock. Removing the explicit screen check therefore gives both
properties:

- while the screen is on, data is at most ~15 minutes old (plus normal
  scheduling delay);
- after unlock, the deferred run executes promptly, which is the refresh.

The residual trade-off: if the device is screen-off but *not* in Doze (for
example charging, or being carried around), the periodic job may still run and
fetch. We accept an occasional background refresh in that state rather than
risking stale data. Strictly forbidding it would require a foreground service
with screen-state receivers.

### Optional battery-optimization exemption

Aggressive OEM battery management can delay or remove an ongoing notification
even when WorkManager is well behaved (issue #4). The main screen therefore
offers a global **Exempt from battery optimization** button. It launches
`Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` with a `package:` URI for
this app; the `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` manifest permission makes
the direct dialog available. Devices without that dialog fall back to
`ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`. The button is replaced by a status
line when `PowerManager.isIgnoringBatteryOptimizations()` reports an active
exemption, and the state is re-read through an Activity Result launcher when the
user returns from the system dialog.

A "Refresh" notification action enqueues a one-off `OneTimeWorkRequest` for
manual refreshes.

## Notification

- Channel `weather`, `IMPORTANCE_LOW`, category string `weather` (Android does
  not define a `CATEGORY_WEATHER` constant).
- `setOngoing(true)`, small icon.
- When `POST_NOTIFICATIONS` is granted mid-session, the app immediately reposts
  from the last stored forecasts and enqueues a one-shot refresh; on startup it
  also re-enables the periodic work when notifications are enabled. This avoids
  the appearance that nothing happened until the next city edit or worker run.
- With exactly one city, title = the real place name and the compact line as the
  notification body.
- With two or more cities, title = app name and one `<place name>: <summary>`
  line per visible city, in the user's current city order. Hidden cities stay in
  the app but are filtered out by `buildStatuses()`, including the timestamp rule.
  With no visible cities, the body is
  the empty-state line.
- Both shapes use `BigTextStyle`. It wraps long single-city summaries and long
  city names instead of ellipsizing them, so no tail is lost on narrow screens.
  `NotificationViewBuilder` decides this shape; `WeatherNotifier` only applies
  it to the Android builder.
- A stale city shows `Weather unavailable` instead of its compact summary. Each
  city's compact line puts the sooner event first:
  - `Sun in 2 h 10 min, no rain` / `Sonne in 2 Std. 10 Min., kein Regen`
  - `Rain in 30 min, sun in 5 h` / `Regen in 30 Min., Sonne in 5 Std.`
  - `Sun for 45 min, rain in 5 h` / `Sonne noch 45 Min., Regen in 5 Std.`
  - `Rain now, no sun` / `Regen jetzt, keine Sonne`
  - `Rain for 10 min (again in 45 min), sun in 2 h` /
    `Regen noch 10 Min. (wieder in 45 Min.), Sonne in 2 Std.`
  - `Snow in 30 min, sun in 10 h 33 min` /
    `Schnee in 30 Min., Sonne in 10 Std. 33 Min.` (without rain)
  - `Snow in 5 min, rain in 30 min, sun in 10 h 33 min` /
    `Schnee in 5 Min., Regen in 30 Min., Sonne in 10 Std. 33 Min.` (with both)
  - `Snow for 1 h 19 min, then rain, no sun` /
    `Schnee noch 1 Std. 19 Min., dann Regen, keine Sonne` (direct handoff)
  Sun is always one of the phrases. Rain and snow each get a phrase whenever they
  have an onset/end in the horizon, so both can appear together in a three-part
  line. If neither has one, the plain `no rain` phrase fills the second slot.
  When the active precipitation ends at exactly the instant the other begins,
  its onset phrase becomes `then rain`/`then snow` (`dann Regen`/`dann Schnee`)
  instead of repeating the same time. A gap between the two keeps both full phrases.
  Ordering uses the event's minutes from the provider's observation time:
  ongoing conditions sort first, events with no change sort last, and ties go
  sun > rain > snow. Every phrase after the first is lowercased so the line reads
  naturally. A second
  rain window inside WetterOnline's 90-minute nowcast is appended to the rain
  phrase as `(again in 45 min)`; hourly-only rain beyond that window never gets
  the hint. The verbose per-condition summaries remain in the app UI only and
  carry the same hint as a separate sentence.
- One-shot onset alerts use the separate `weather_alerts` channel. Sun, rain and
  snow each have their own per-city enable flag, lead time, `AlertKey` state and
  WorkManager job name, so independent episodes never collide — a city with both
  rain and snow forecast gets both alerts at their own onset times. The shared
  compact line merely lists all forecast conditions side by side; it never
  suppresses an alert. Alert states and lead
  times are DataStore JSON with default-off/absent values for old installs.
- Freshness: each city stores its own `fetchedAtMillis`. The notification uses
  the oldest of the shown timestamps via `setWhen()` and `setShowWhen(true)`.
  For a live "time since update" indicator, also use `setUsesChronometer(true)`:
  SystemUI then renders an automatically ticking elapsed time since that
  timestamp, with no extra work from the app.
  Do **not** put a literal `"Updated 25 min ago"` string in the notification
  text — it is a snapshot and would freeze until the next WorkManager run, and
  WorkManager cannot tick more often than every 15 minutes.
- Tapping the notification body opens `MainActivity` directly via a
  `PendingIntent` with `CLEAR_TOP | SINGLE_TOP`, reusing an existing task.
  Actions: **Refresh** only.
- On Android 13+ request `POST_NOTIFICATIONS` on first launch.

## Widget

A Jetpack Glance (1.2.0) `GlanceAppWidget` is registered through
`WeatherWidgetReceiver` with a 4×2 target size and a 30-minute system update
floor as a fallback. It never fetches: `provideGlance()` reads the same DataStore
forecasts as the UI and builds a `WidgetSnapshot` from the pure
`widgetSnapshot()` mapper.

- **City selection**: `widget_city` DataStore key, set by the per-city **Show in
  widget** switch. It is single-select (choosing another city replaces the old
  choice); clearing it and invalid/hidden/unknown values fall back to the first
  visible city. Removing a city clears the key if it was the selected one.
- **Content**: display name, compact summary, absolute `Updated HH:MM` (a
  snapshot does not tick), the 48-hour grid as two 24-hour rows labelled with the
  weekday of each row's first cell, and the `90` row when at least one future
  cell is sun/rain/snow. Sunrise/sunset markers are omitted at this cell size.
  Elapsed cells are filtered at render time; a fully elapsed grid or nowcast
  shows the existing `48 h outdated` / `outdated` hints.
- **Colours and descriptions**: `HourKind.color()`/`label()` live in
  `WeatherPresentation.kt`, shared with the in-app grid so the widget cannot
  drift. Each cell carries the same localized content description as the app.
- **RemoteViews limit**: a Glance `Row`/`Column` may have at most ten children.
  The hour rows therefore use one label plus four nested group columns, each
  holding one row of six cells; the `90` row nests its cells the same way.
- **Updates**: `updateWeatherWidget()` calls `updateAll()` after a successful
  worker pass and after city add/remove, visibility, order or widget-city
  changes. `WeatherWidgetReceiver.onUpdate()` also renders from stored state
  when the widget is first placed. Tapping anywhere opens `MainActivity`; there
  is no refresh action.
- **Freshness trade-off**: the widget redraws on the 15-minute refresh cadence,
  so past colours can linger for up to that long. Adding more frequent widget
  work solely to blank cells would cost battery, so it is intentionally not
  done.

## Lifecycle

- A `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` receiver re-enqueues the periodic
  work and reposts the last known notification. These broadcasts are exempt
  from Android's implicit-broadcast restrictions.
- A setting in the app enables/disables updates; disabling cancels the work and
  removes the notification.
- After a user force-stops the app, Android will not restart it until the user
  opens it again; this is accepted behaviour.

## Error handling

- Keep the last successful forecast **per city** when a fetch or parse fails.
- Handle: network errors, HTTP errors, missing `ng-state`, invalid JSON, missing
  shortcast key, empty forecast, and unknown symbol codes.
- Log parse errors with the symbol code / URL so markup changes are detectable.
- Avoid duplicate concurrent fetches; WorkManager already serialises the work.

## Build and test

The Gradle wrapper is checked in. Point `local.properties` at your Android SDK
(it is gitignored):

```properties
sdk.dir=/path/to/Android/Sdk
```

Then:

```bash
./gradlew :app:testDebugUnitTest
./gradlew :app:assembleDebug
```

Use a JDK that provides `javac` (Android Studio's bundled JBR works). The upload
script picks one automatically: a valid `JAVA_HOME` first, then
`/opt/android-studio/jbr`, then `javac` on `PATH`. The unit tests reuse the
trimmed real payload from `tests/fixtures/shortcast.json` and do not hit the
network.

`scripts/upload-debug-apk.sh [tag]` builds the same debug APK and attaches it to
a GitHub pre-release with `gh release upload`. With no argument it generates a
local timestamp tag `YYYYMMDD-HHMMSS`, so every run creates a new release; an
explicit tag can be any valid Git ref. The script creates the release on
GitHub's default branch if the tag is new and overwrites the APK when the tag
already exists; a local-only `HEAD` is never used as the target. Two useful
explicit schemes are `v<version>-debug[-n]`
(`v0.1.0-debug`, `v0.1.0-debug-2`, …) for version-aligned builds and
`YYYYMMDD-HHMMSS` (`20261121-211942`) for timestamp builds, which sort
chronologically. It requires an authenticated `gh` CLI and warns when the
working tree is dirty or local commits are unpushed, since then the APK may not
match the release commit. The APK is never committed to the repository.

## Open questions / out of scope

- Location-based city detection, or very large city lists (each city needs two
  HTTP requests per refresh).
- Notification icons / small weather images.
- Computing sunrise/sunset astronomically: the provider's own `astro/days` data
  is used instead, so the times match WetterOnline.
- WetterOnline terms of service and attribution requirements for scraping.
- Making the instant-unlock behaviour exact (would require revisiting the
  foreground-service decision).
