# Sonnenregen Android app

## Goal

Sonnenregen should also be a native Android app showing a permanent notification
with both forecasts for one or more locations (default: Berlin):

- how long until the sun shines, or until the current sunshine ends;
- how long until it rains, or until the current rain ends.

The app fetches and parses the WetterOnline pages itself. It does **not** depend
on the Python HTTP service in this repository. That service remains useful as a
reference implementation and for debugging, but the mobile app is standalone.

## Platform decisions

- **Kotlin + Jetpack Compose**, minSdk 26 (or enable core library desugaring if
  supporting older versions, for `java.time.OffsetDateTime`).
- **WorkManager** for periodic work. A 15-minute interval is the minimum
  supported by WorkManager, and is accepted for this app. This avoids
  foreground-service restrictions entirely.
- No foreground service. `ACTION_USER_PRESENT` / `ACTION_SCREEN_ON` are not
  exempt implicit broadcasts on API 26+, so a manifest receiver cannot reliably
  trigger an immediate refresh. Instead we rely on Doze: WorkManager jobs are
  deferred while the device is in Doze and are run when it becomes active again,
  so a pending 15-minute job normally executes shortly after unlock. This gives
  refresh-on-unlock without an FGS. If truly exact unlock timing is required,
  that is a separate design change involving a foreground service and its
  Android 12+/15+ constraints.
- The notification is still "permanent" in the sense that it is posted as an
  ongoing notification (`setOngoing(true)`); the system keeps it visible even
  when the app process is killed.

## Localization

All user-facing text lives in Android resources. `values/strings.xml` is the
English fallback; `values-de/strings.xml` contains the German translation.
Android selects the translation from the device locale, so a German-locale
device gets German text and other locales keep the English fallback.

The forecast wording is generated by `ForecastFormatter` from `ForecastPhrases`,
which reads the templates from resources. The domain model only carries
structured data (`Change`, `Condition`, `minutes`), never display strings.
German durations use `Std.`/`Min.` instead of `h`/`min`:

- `Sonne in 2 Std. 10 Min., kein Regen`
- `Regen in 30 Min., Sonne in 5 Std.`

## Multiple cities

The user can add and remove WetterOnline city slugs in the app. `normalizeCity()`
trims/lowercases input and `isValidCitySlug()` validates it with
`^[a-z0-9]+(?:-[a-z0-9]+)*$` before any URL is built. Slugs remain lowercase in
storage; `displayCity()` capitalises the first letter for the UI and notification
(`berlin` → `Berlin`, `frankfurt-am-main` → `Frankfurt-am-main`). DataStore holds:

- `cities`: a JSON array in the order the user added them;
- `forecasts_by_city`: a JSON map from slug to the last good formatted forecast.

The original single-city keys are read once and migrated on first access, so an
existing installation keeps its Berlin forecast after the upgrade.

One worker run fetches every configured city concurrently. Each city is handled
independently:

- a successful city replaces its stored forecast;
- a failed city keeps its last good forecast and is marked stale for that
  notification only;
- the run succeeds if any city succeeded, retries if every failure was a network
  error, and fails if every failure was a parse/validation error.

Adding a city enqueues an immediate refresh; removing one reposts the notification
without a network request. With no cities configured the notification shows an
empty-state line.

## 48-hour colour overview

Each city card also shows a colour-only forecast grid: 48 one-hour cells from the
current hour, grouped into four blocks of six per calendar day in `Europe/Berlin`.
An evening start therefore produces three rows (part of today, all of tomorrow,
part of the day after); exactly midnight produces two. A slightly larger gap
every six hours is the only orientation aid — no date prefix and no `00`/`06`/
`12`/`18` labels — and no scrolling is needed.

The grid reads purely as weather at a glance. A clear night counts as clouds,
not sun:

- bright/pale yellow — sunny / partly sunny;
- very light gray — all clouds and clear nights, regardless of cloud intensity;
- light/medium/dark blue — light rain / rain / heavy rain.

For example, `so` is bright yellow, `mo` (clear night) is very light gray like
clouds, and `mb` and `wb` are both pale yellow. Sunrise/sunset stay in the text
line instead of being encoded as glyphs. No weather icons or labels are drawn;
each cell carries a localized `contentDescription` for screen readers. The
overview is stored as `CityForecast.hours` (defaulting to an empty list), so
existing installs simply show no grid until their next refresh. Legacy night
enum values from the first grid version still decode; `CLEAR_NIGHT` now renders
gray like clouds. The notification is unchanged.

## Data source and parsing

The app fetches both pages with OkHttp (or Ktor), concurrently:

```
https://www.wetteronline.de/wettertrend/{city}
https://www.wetteronline.de/90-minuten-wetter/{city}
```

Use a normal browser-like `User-Agent` and `Accept-Language: de-DE`.

Each page is an Angular SSR app. Parse the embedded state with a regex:

```kotlin
Regex("""(?is)<script[^>]*\bid=["']ng-state["'][^>]*>(.*?)</script>""")
```

Then:

1. JSON-decode the captured script content with `kotlinx.serialization`
   (`ignoreUnknownKeys = true`).
2. Find the state entries whose keys contain `/blending/shortcast/v1?` and
   `/astro/days/v1?`. The latter carries exact per-day `sun.rise` / `sun.set`
   timestamps (and is optional — polar days have neither).
3. Read `current`, `nowcast_trend.items` (15-minute slots) and `hours`
   (1-hour slots). Each item has an ISO-8601 `date` and a `symbol` code.
4. Stitch the 15-minute grid to the hourly grid, as in the Python reference:
   use the fine grid for the near future and stretch its last slot to the next
   full hour.
5. Classify each slot:
   - **sunshine**: symbol starts with `so` or `wb`, and for the current
     observation `solarElevation > 0`;
   - **rain**: symbol contains `r`, `s` or `g` after the first two characters,
     but not snow (`n`).
6. Split the timeline at sunrise/sunset and mark the parts that are in daylight.
   WetterOnline labels the whole hour containing sunrise with a night symbol
   (e.g. `mo` = *klar*); on the daylight side of the cut we use the matching day
   symbol (`so` = *sonnig*). This makes a clear night start sunshine at the
   exact sunrise instead of at the next hourly grid boundary. Cloudy night
   symbols (`mw` → `bw`) still delay sunshine until a genuinely sunny slot, and
   a sunny slot can never extend past sunset.
7. Walk forward from the provider's `current.date` to the first slot where each
   condition changes. Produce `currently`, `event` (`starts` / `ends`), `at`,
   `minutes`, and a human-readable summary. The next sunrise and sunset are also
   carried on the forecast and shown in the app UI (not in the notification).

City slugs are normalized and validated by the shared helpers in `domain/City.kt`
before building URLs.

## Refresh behaviour

`WeatherWorker` is enqueued as a `PeriodicWorkRequest` with a 15-minute interval
and constraints `NetworkType.CONNECTED`, not requiring charging or idle.

On each run:

1. Fetch and parse both pages for **each** configured city, concurrently. Do
   **not** skip the run based on `PowerManager.isInteractive()`; see the note
   below.
2. On success, persist that city's result plus timestamp in DataStore and include
   it in the notification.
3. On failure, keep that city's last good result, show `Weather unavailable` for
   it, and let WorkManager retry with backoff. Other cities are unaffected.

### Why the worker must not skip while the screen is off

An early draft had the worker check `isInteractive()` and do nothing when the
screen was off. That is a staleness bug: WorkManager's periodic run happens at a
wall-clock cadence, so if every screen-on period is short and misses those
moments, the worker can skip indefinitely and the notification never updates.

Doze already provides the desired "idle while screen off" behaviour for the
common case: a phone that is unplugged, stationary and screen-off enters Doze,
WorkManager/JobScheduler defers periodic jobs, and the pending job runs when the
device wakes on unlock. Removing the explicit screen check therefore gives both
properties:

- while the screen is on, data is at most ~15 minutes old (plus normal
  scheduling delay);
- after unlock, the deferred run executes promptly, which is the refresh.

The residual trade-off: if the device is screen-off but *not* in Doze (for
example charging, or being carried around), the periodic job may still run and
fetch. We accept an occasional background refresh in that state rather than
risking stale data. Strictly forbidding it would require a foreground service
with screen-state receivers.

A "Refresh" notification action enqueues a one-off `OneTimeWorkRequest` for
manual refreshes.

## Notification

- Channel `weather`, `IMPORTANCE_LOW`, category string `weather` (Android does
  not define a `CATEGORY_WEATHER` constant).
- `setOngoing(true)`, small icon.
- With exactly one city, keep the original style: title = city name, compact line
  as the notification body.
- With two or more cities, title = app name and `InboxStyle` with one
  `City: <summary>` line per city, in the order the user added them. With no
  cities, the body is the empty-state line. `NotificationViewBuilder` decides
  this shape; `WeatherNotifier` only applies it to the Android builder.
- A stale city shows `Weather unavailable` instead of its compact summary. Each
  city's compact line puts the sooner event first:
  - `Sun in 2 h 10 min, no rain` / `Sonne in 2 Std. 10 Min., kein Regen`
  - `Rain in 30 min, sun in 5 h` / `Regen in 30 Min., Sonne in 5 Std.`
  - `Sun for 45 min, rain in 5 h` / `Sonne noch 45 Min., Regen in 5 Std.`
  - `Rain now, no sun` / `Regen jetzt, keine Sonne`
  Ordering uses the event's minutes from the provider's observation time.
  Ongoing conditions sort first, events with no change sort last, and sun wins
  ties. The second phrase is lowercased so the line reads naturally. The verbose
  per-condition summaries remain in the app UI only.
- Freshness: each city stores its own `fetchedAtMillis`. The notification uses
  the oldest of the shown timestamps via `setWhen()` and `setShowWhen(true)`.
  For a live "time since update" indicator, also use `setUsesChronometer(true)`:
  SystemUI then renders an automatically ticking elapsed time since that
  timestamp, with no extra work from the app.
  Do **not** put a literal `"Updated 25 min ago"` string in the notification
  text — it is a snapshot and would freeze until the next WorkManager run, and
  WorkManager cannot tick more often than every 15 minutes.
- Actions: **Refresh** and **Open app**.
- On Android 13+ request `POST_NOTIFICATIONS` on first launch.

## Lifecycle

- A `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` receiver re-enqueues the periodic
  work and reposts the last known notification. These broadcasts are exempt
  from Android's implicit-broadcast restrictions.
- A setting in the app enables/disables updates; disabling cancels the work and
  removes the notification.
- After a user force-stops the app, Android will not restart it until the user
  opens it again; this is accepted behaviour.

## Error handling

- Keep the last successful forecast **per city** when a fetch or parse fails.
- Handle: network errors, HTTP errors, missing `ng-state`, invalid JSON, missing
  shortcast key, empty forecast, and unknown symbol codes.
- Log parse errors with the symbol code / URL so markup changes are detectable.
- Avoid duplicate concurrent fetches; WorkManager already serialises the work.

## Build and test

The Gradle wrapper is checked in. Point `local.properties` at your Android SDK
(it is gitignored):

```properties
sdk.dir=/path/to/Android/Sdk
```

Then:

```bash
./gradlew :app:testDebugUnitTest
./gradlew :app:assembleDebug
```

Use a JDK that provides `javac` (Android Studio's bundled JBR works). The unit
tests reuse the trimmed real payload from `tests/fixtures/shortcast.json` and do
not hit the network.

## Open questions / out of scope

- Location-based city detection, or very large city lists (each city needs two
  HTTP requests per refresh).
- Notification icons / small weather images.
- Computing sunrise/sunset astronomically: the provider's own `astro/days` data
  is used instead, so the times match WetterOnline.
- WetterOnline terms of service and attribution requirements for scraping.
- Making the instant-unlock behaviour exact (would require revisiting the
  foreground-service decision).
